# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- Run the CLI: `pnpx tsx index.ts <command>` (or `pnpm run run`)
- Initialize a new knowledge base: `pnpx tsx index.ts init <dir>` — writes a template tree (`problems/`, `readme.md`, `.mylearn/config.json`)
- Global note selection: every note-taking verb takes `-p, --problem <problem>` — a note path (absolute, CWD-relative, project-relative, or `problems/`-relative) or a pattern matching exactly one note title dir (case-insensitive substring; 0 matches → error, >1 → lists them). Declared on `program` *and* on each consuming subcommand so both positions work: `-p <x> <verb>` and `<verb> ... -p <x>`. Resolution lives in `src/ai/problems.ts` (`resolveNote`).
- Luogu provider CLI: `pnpx tsx index.ts luogu fetch <source> [-c <category>]` — pid or Luogu problem URL, default category `luogu` (fetcher parses the page's `lentille-context` JSON payload; writes `problems/<category>/<title>/` and prints the saved path); `pnpx tsx index.ts luogu submit <solution.cpp> -p <problem>` — compiles with `g++` (execFile, no shell; external system dependency), validates against the note's `### 样例` input/output blocks (passes when normalized stdout matches), and on success archives the solution (copies the .cpp as a source file + writes a solution markdown with the code; exits 1 and saves nothing on failure).
- PDF provider CLI: `pnpx tsx index.ts pdf import <file> -c <category>` — converts a local PDF via the `markitdown` CLI (external system dependency, throws when missing) and saves it as a note. Each provider fetcher declares `canFetch(source)` (capability test, no global registry — the source domain is chosen by the CLI verb).
- AI provider: `pnpx tsx index.ts ai "<prompt>" [-p <problem>]` hands the prompt to the `ai-client-prefix` client (config `ai-client-prefix` in `.mylearn/config.json`, space-separated; default `codex` — e.g. `codex --yolo`, `claude -p`; the message is the last arg). Spawned with stdio inherited and exit code propagated (missing client → clear error, exit 1). With `-p` the bundle adds the note (task + problem statement + samples); always prefixed with a pointer to `docs/SKILL.md` (the agent-facing workflow doc; skill-format — the CLI is the single contract, there is no MCP server).
- Maintain: `pnpx tsx index.ts maintain watch` — one-shot: diffs `problems/` against `.mylearn/index/latest.json` (mtime comparison, re-hash changed files with sha256), persists the new snapshot and prints added/changed/removed. `pnpx tsx index.ts daemon` — the long-running version: one-shot diff at start, then keeps the snapshot fresh (debounced `fs.watch`); Ctrl-C stops. `pnpx tsx index.ts maintain luogu -p <problem>` dispatches to the provider's `maintain(Problem)` — re-validates every C++ source saved in the note.
- Typecheck: `pnpm exec tsc --noEmit` (note: `pnpx tsc` resolves the wrong package, use `pnpm exec tsc`).
- Tests: `pnpm test` — built-in `node:test` runner via `tsx --test`, no extra deps; suites are `tests/fetch.test.ts` (fetcher `canFetch` matrix, mocked redirects, live conversions, end-to-end store), `tests/maintain.test.ts` (watch snapshot diff, sample parsing, g++-backed validate/submit/maintain — compiled cases skipped without g++) and `tests/ai.test.ts` (note resolution and prompt assembly — fully offline). Some fetch cases hit the network (Luogu). To filter (note: the flag must precede the file path): `pnpx tsx --test --test-name-pattern "canFetch|watch|parseSamples|resolveNote" tests/fetch.test.ts tests/maintain.test.ts tests/ai.test.ts` (offline-only); network cases are in suites named `conversion (live network)` and `end to end`. No lint or build step; TypeScript runs directly via `tsx`.

**Startup requirement:** `index.ts` imports `src/utils/global.ts`, which exits the process (exit code 1) unless `.mylearn/config.json` exists — at `MYLEARN_PROJECT` when that env var is set, otherwise in the *current working directory*. The CLI must be run from inside an initialized project (e.g. `data/`, gitignored); set `MYLEARN_PROJECT` to pin the project when spawning from a different CWD (scripts, agents). `init` writes the project at the path passed as argument, but the startup check still uses CWD.

## Architecture

A CLI for managing a personal competitive-programming problem knowledge base: problems and solutions live on disk as markdown files under a category-organized tree.

- **Entry** — `index.ts` imports `src/utils/global.ts` (loads `.mylearn/config.json` into `globalThis.projectConfig`, sets `globalThis.projectRoot`), then `src/utils/arg.ts` (commander, `.ts`-extension imports). New subcommands are registered here.
- **Domain model** — `src/utils/problem.ts` is pure interfaces, no IO: `NoteFile` (title, description, `sourceFiles`), `Solution`, `Problem` (adds `category`, `solutions`).
- **Persistence/layout** — `src/utils/persist.ts` is the single source of truth for where things live (`problems/<category>/<title>/` with `problem.md` holding `title`/`category` frontmatter via gray-matter, `<title>.md` per solution, copied source files; `problems/notes/` holds nestable freeform notes without a problem statement — skipped by `listProblems`, no special handling elsewhere) and owns all disk reads/writes (`createProblem`, `listSolutions`, `addSolutionFile`, etc.). Root is always passed as a parameter — the model never captures `globalThis.projectRoot`.
- **File-backed proxies** — `src/utils/noteFile.ts` returns live `Problem`/`Solution` objects (`openProblem(dir)`, `openSolution(path)`) backed by a JS `Proxy`: gets redisk (frontmatter/body, `solutions` from directory listing), and setting `title`/`category`/`description` writes through to `problem.md` immediately. Structural mutations (`solutions`, `sourceFiles`) go through `persist.ts` helpers, not `set`.
- **Fetchers** — every provider owns its fetcher at `provider/<name>/fetch.ts` (a `Fetcher` object: `canFetch(source)` + `convert(source): Promise<Draft>`, `Draft`/`Fetcher` types and the `importDraft(root, category, draft)` save pipeline live in `src/utils/fetcher.ts` — convert → createProblem → openProblem). `pdf/fetch.ts` shells out to the `markitdown` CLI (external system dependency), throwing if it's unavailable; `luogu/fetch.ts` fetches a Luogu page and parses its `lentille-context` Serde JSON payload (pid, contenu sections, samples).
- **Project scaffolding** — `src/project/init.ts` recursively creates the template tree, erroring if a path exists with the wrong kind (file vs dir).
- **Providers** — domain modules own their CLI, fetchers, and maintain logic. `src/utils/program.ts` exports the shared commander instance (own module so providers don't create an import cycle with `arg.ts`); importing `../provider/luogu/index.ts`, `../provider/pdf/index.ts` and `../provider/ai/index.ts` in `arg.ts` self-registers `luogu fetch`/`luogu submit`, `pdf import` and `ai` on it. The `maintain` verb dispatches provider subcommands (`maintain luogu -p <problem>`) to `provider/<provider>/maintain.ts`'s `maintain(Problem)` — the model stays pure; the provider resolves the note dir from `globalThis.projectRoot` + category/title.
- **Note resolution & the AI provider** — `src/ai/problems.ts` is the base every provider's `-p` consumer shares: `listProblems` (walks `problems/<cat>/<title>/problem.md`), `resolveNote` (path candidates first: absolute/CWD/project/problems-relative, then pattern with exactly-one-match enforcement), `openNote` (resolve + `openProblem` proxy). The AI provider's only surface is the `ai "<prompt>" -p` verb (`src/provider/ai/index.ts`): `buildPrompt` (`src/provider/ai/prompt.ts`) assembles the bundle from the note, then the verb spawns `codex` with it (plus the `docs/SKILL.md` pointer) and propagates its exit code. Agents drive the knowledge base through the CLI — the workflow doc is `docs/SKILL.md`.
- **Maintain** — `src/maintain/watch.ts` snapshots `problems/` into `.mylearn/index/latest.json` (per-file mtime + sha256; a file is re-hashed only when its mtime changed) — `watch(root): NoteDiff` one-shot, `watchContinuous(root, onChanges, debounceMs)` returns a stop function the `daemon` verb's SIGINT handler calls (natural exit, no `process.exit` truncation). The luogu validation engine lives in `src/provider/luogu/maintain.ts`: parses `### 样例` sections from a note description, compiles via g++ (run each sample input on stdin, compare normalized stdout; timeout → TLE, nonzero exit → runtime error), plus `submitSolution` (validate + archive) and `maintain(Problem)` (re-validate every saved C++). Note: `-p`-based note lookup in the luogu provider was unified onto `resolveNote`; there is no longer a `findProblemByPid`.

### In-progress work (empty placeholder files)

`src/project/scan.ts`, `src/project/search.ts`, and `src/project/review.ts` are empty stubs. `search.ts`/`review.ts` can consume `openProblem`; `scan.ts` can rebuild the index from the snapshot `watch` writes. Providers are the pattern for new domains: `src/provider/<name>/index.ts` (self-registering CLI + fetcher), `fetch.ts` (`canFetch`/`convert`), `maintain.ts` (`maintain(Problem)`), as in `src/provider/luogu/`. `parseFrontMatter.ts` is obsolete — the proxy's gray-matter reading in `persist.ts`/`noteFile.ts` supersedes it. `init.ts` still writes the template's `Problem 1/Problem 1.md` layout while notes are written as `problem.md` (pre-existing inconsistency). Check git status before assuming a module is implemented.

## Conventions

- ES modules (`"type": "module")`; `tsconfig.json` uses `module: nodenext` with `allowImportingTsExtensions` + `rewriteRelativeImportExtensions` — relative imports **must** keep explicit `.ts` extensions (`import x from "../utils/global.ts"`).
- `package.json` `main: index.js` is stale; the real entry is `index.ts` executed via tsx.
